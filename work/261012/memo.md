# 第3問：別のサーバーを呼ぶ API を設計する（10/12 月 〜 10/16 金）

自分の API（Gateway）が、裏にある別のサーバー（Upstream）を `HttpClient` で呼び、2つの結果をまとめて返す。
実務でよくある形（BFF・中継 API）で、**ネットワークと設計が同じ題材の中に出てくる**。

- ネットワーク側: 呼んだ先の失敗・遅延・停止を、自分の API の応答（ステータスコード）にどう変えるか。
- 設計側: 「HTTP の受け答え」「まとめる規則」「外を呼ぶ処理」をどう分けるか。DI でどう組み立てるか。

第2問で学んだこと（`HttpClient`、`async` / `await`、`Task.WhenAll`、ステータスコードと例外）を、**呼ぶ側を設計する材料** として使い直す。
**学習の中心は Gateway。** Upstream は決まった応答を返すだけの最小限にする。

テーマとする技術・考え方:

- 責務分離: 1つのクラスに1つの役割だけを持たせること。
- インターフェース（`interface`）: 「何ができるか」だけを決めた型。C++ の純粋仮想関数だけを持つクラスに近い。
- DI（依存性の注入）: クラスが使う相手を自分で `new` せず、外から渡してもらう仕組み。ASP.NET Core に組み込まれている。
- `IHttpClientFactory` と型付きクライアント: `HttpClient` の作成と使い回しを DI に任せる仕組み。第2問で「名前と目的だけ」調べたもの。
- 502 Bad Gateway / 504 Gateway Timeout: 「自分は動いているが、呼んだ先が失敗した／間に合わなかった」ことを表すステータスコード。
- 部分的な失敗: 2つのうち1つだけ失敗したとき、全体を失敗にするか、取れた分だけ返すかの判断。

## 構成


- Gateway の動作確認には `.http` ファイル（VS 2026 でリクエストを送れるテキストファイル）か curl を使う。
  `Gateway/Gateway.http` を自分で作り、送ったリクエストを残していく。

## Upstream の仕様（作るのはこれだけ）

商品（`Id`, `Name`, `Price`）と在庫（`ProductId`, `Quantity`）を、コードの中に固定で持つ。
どちらのエンドポイントも、応答を返す前に `Task.Delay` で待つ。

| エンドポイント | 待ち時間 | 応答 |
|---|---|---|
| `GET /products/{id}` | 500 ms | 商品（200）。なければ 404 |
| `GET /stock/{id}` | 800 ms | 在庫（200）。なければ 404 |

失敗を再現するため、ID によって在庫の動きを変える。

| ID | 商品 | 在庫 |
|---|---|---|
| 1, 2 | あり | あり（通常どおり） |
| 3 | あり | 500 を返す |
| 4 | あり | 5 秒待ってから返す（遅すぎる） |
| 上記以外 | 404 | 404 |

## Gateway の仕様（最終形）

| エンドポイント | 応答 |
|---|---|
| `GET /catalog/{id}` | 商品と在庫をまとめた JSON |

応答の例（ID=1）:

```json
{ "id": 1, "name": "apple", "price": 200, "quantity": 12 }
```

失敗したときの応答は、水曜に自分で設計する（下の「水 10/14」）。

### 火 10/13：役割ごとにクラスを分け、DI で組み立てる

月曜の書き出しをもとに、次の3つに分ける。**推奨の分け方** は次のとおり。

| 役割 | クラス | 知っていること | 知らないこと |
|---|---|---|---|
| HTTP の受け答え | `Program.cs` のエンドポイント | Gateway の URL、返すステータスコード | Upstream の存在 |
| まとめる規則 | `CatalogService` | 商品と在庫を組み合わせる規則 | HTTP、Upstream の URL |
| 外を呼ぶ処理 | `IUpstreamClient` と `UpstreamClient` | Upstream の URL とパス、JSON の形 | まとめる規則 |

- `CatalogService` は `IUpstreamClient`（インターフェース）だけを知る。コンストラクタの引数で受け取る。
- `UpstreamClient` は `HttpClient` を自分で `new` せず、コンストラクタで受け取る。登録は型付きクライアントで行う。

```csharp
// 登録の形の例（BaseAddress をどこに書くかは自分で決める）
builder.Services.AddHttpClient<IUpstreamClient, UpstreamClient>(client =>
{
    client.BaseAddress = new Uri("http://localhost:xxxx");
});
```

- Upstream の URL は、コードに直接書かずに `appsettings.json` に置く。読み方は自分で調べる（`builder.Configuration`）。
- `CatalogService` の中で、商品と在庫を **並行して** 呼ぶ（`Task.WhenAll`）。月曜と応答時間を比べる。

**終わったと判断する目印:**

- `Program.cs` に `new HttpClient` も Upstream の URL も出てこない。
- ID=1 の応答時間が、月曜より短くなる。何 ms になるかを先に予想してから確かめる。

### 水 10/14：エラーの設計

Upstream の失敗を、Gateway の応答にどう変えるかを決めて実装する。

**1. `UpstreamClient` は失敗をどう伝えるか**

`UpstreamClient` は、1回の呼び出しの結果を次のどれかとして返す。表し方の候補は2つ。**推奨は (A)**。

| 結果 | 起きる場面 |
|---|---|
| 成功 | 200 |
| 見つからない | 404 |
| 上流の失敗 | 5xx、または接続できない |
| 時間切れ | タイムアウト |

- (A) 結果を表す型を返す（`abstract record` を親にして、子の `record` を作る）。
- (B) 失敗の種類ごとに自作の例外を投げ、上で catch する。
- (A) を選んだら、(B) と比べた長所と短所を1つずつメモ欄に書く。

**2. Gateway は何を返すか**

次の表の「Gateway の応答」を **自分で決めて埋める**。理由もメモ欄に書く。

| ケース | 再現方法 | Gateway の応答 |
|---|---|---|
| 商品が見つからない | ID=99 | |
| 在庫が 500 | ID=3 | |
| 在庫が遅すぎる | ID=4 | |
| Upstream が止まっている | Upstream を停止 | |

考えるときのヒント:

- 404 は「Gateway の `/catalog/99` が存在しない」という意味になる。Upstream の 404 をそのまま返してよい場面か。
- 502 と 504 は「Gateway のせいではない」ことを呼ぶ側に伝えられる。500 との違いは何か。
- 在庫だけ取れないとき、商品情報だけでも返す（`"quantity": null`）のと、全体を失敗にするのと、どちらが使う側にとってうれしいか。**正解は1つではない。** どちらかに決めて理由を書く。

**3. タイムアウト**

- `AddHttpClient` の設定で `HttpClient.Timeout` を 2 秒にする。ID=4 で、在庫の待ちが 2 秒で打ち切られることを確かめる。
- エラーの本文は `ProblemDetails`（エラーの内容を JSON で返す標準の形）にする。`Results.Problem(...)` を調べて使う。

**終わったと判断する目印:** 4つの失敗ケースが、自分で決めた応答で返り、Gateway のコンソールに例外のスタックトレースが出ない。

### 木 10/15：崩して確かめる

1つずつ変えて、何が起きるかを確かめる。**先に予想を書いてから** 試し、確かめたら元に戻す。

- **差し替え:** `IUpstreamClient` を実装した `FakeUpstreamClient` を作る。ネットワークを使わず、決まった値を返すだけのクラス。
  登録の1行だけを差し替えて、Upstream を止めたまま Gateway が動くか確かめる。`CatalogService` を1行も変えずに済んだか。
  - これが「依存の向き」の確認で、来週以降の単体テストの土台になる。
- **`new` に戻す:** `CatalogService` の中で `UpstreamClient` を直接 `new` するように戻す。上の差し替えをもう一度やろうとすると、どこを直すことになるか。
- **並行をやめる:** `Task.WhenAll` をやめて1件ずつ `await` に戻す。ID=4 の応答時間はどう変わるか。
- **タイムアウトの置き場所:** `HttpClient.Timeout` の代わりに、`CancellationTokenSource` で Gateway 全体に 1 秒の制限をかける。ID=1 はどうなるか。タイムアウトを「1回の呼び出しごと」にかけるのと「リクエスト全体」にかけるのとで、何が違うか。

## 書き方の決まり

- 第2問の決まり（`.Result` / `.Wait()` を使わない、`async void` を使わない）を引き継ぐ。
- `CatalogService` には HTTP に関わる型（`IResult`、`HttpClient`、ステータスコード）を出さない。
- 依存する相手（`IUpstreamClient`、`HttpClient`）はコンストラクタで受け取る。自分で `new` しない（木曜に試すときだけ例外）。
- `Program.cs` には「登録」と「エンドポイント」だけを書く。
- 例外を catch して何もせずに捨てない。
