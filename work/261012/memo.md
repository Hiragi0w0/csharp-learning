# 第3問：責務を分けた小さなタスク管理 API（10/12 月 〜 10/16 金）

タスク（やること）を登録・取得・完了・削除できる Web API を、新しく1つ作る。
最初は全部を `Program.cs` に書き、そこから **役割ごとにクラスを分けていく**。
今週の学習の中心は機能ではなく **設計**（責務の分け方、依存の向き、エラーの返し方）。

テーマとする技術・考え方:

- 責務分離: 1つのクラスに1つの役割だけを持たせること。
- インターフェース（`interface`）: 「何ができるか」だけを決めた型。C++ の純粋仮想関数だけを持つクラスに近い。
- DI（依存性の注入）: クラスが使う相手を自分で `new` せず、外から渡してもらう仕組み。ASP.NET Core に組み込まれている。
- サービスの寿命: DI に登録するときの `AddSingleton` / `AddScoped` / `AddTransient` の違い。
- エラーの設計: 入力の誤り・存在しない・状態の矛盾を、ステータスコード（400 / 404 / 409）で返し分ける。
- `ProblemDetails`: エラーの内容を JSON で返すときの標準的な形（RFC 9457）。

## API の仕様

タスクは `Id`（int）、`Title`（string）、`IsDone`（bool）を持つ。

| エンドポイント | 成功時 | 失敗時 |
|---|---|---|
| `GET /tasks` | 全件（200） | — |
| `GET /tasks/{id}` | 1件（200） | なければ 404 |
| `POST /tasks` 本文 `{ "title": "..." }` | 作成したタスク（201） | タイトルの誤りは 400 |
| `PUT /tasks/{id}/done` | 完了にしたタスク（200） | なければ 404、すでに完了なら 409 |
| `DELETE /tasks/{id}` | 本文なし（204） | なければ 404 |

タイトルの規則:

- 前後の空白は取り除いて保存する。
- 取り除いたあとで空なら誤り。
- 50 文字を超えたら誤り。
- `Id` はサーバーが 1 から順に振る。削除した番号は使い回さない。

### 火 10/13：役割ごとにクラスを分け、DI で組み立てる

月曜の問いの答えをもとに、次の3つに分ける。**推奨の分け方** は次のとおり。

| 役割 | クラス | 知っていること | 知らないこと |
|---|---|---|---|
| HTTP の受け答え | `Program.cs` のエンドポイント | URL、ステータスコード | データの保存方法 |

```csharp

builder.Services.AddSingleton<ITaskRepository, InMemoryTaskRepository>();
```

- エンドポイントは引数に `TaskService` を書くと、DI から受け取れる。

### 水 10/14：エラーの設計

タイトルの規則と「すでに完了」を実装し、400 / 404 / 409 を返し分ける。

- 規則の判定は `TaskService` に書く。**`TaskService` は HTTP を知らない** ので、`Results.NotFound()` などの `IResult` を返してはいけない。
- では、`TaskService` は失敗をどうやってエンドポイントに伝えるか。候補は2つ。**推奨は (A)**。
  - (A) 結果を表す型を返す。成功・入力の誤り・見つからない・状態の矛盾を、型で区別する（`abstract record` を親にして子の `record` を作る形が書きやすい）。
  - (B) 失敗の種類ごとに自作の例外を投げ、エンドポイントで catch する。
  - (A) を選んだら、(B) と比べた長所と短所を1つずつメモ欄に書く。
- エンドポイントで、結果の種類をステータスコードに変換する。エラーの本文は `ProblemDetails` の形にする。
  - 400 は `Results.ValidationProblem(...)`、404・409 は `Results.Problem(...)` を調べて使う。
- `.http` に失敗のケースを足す: 空白だけのタイトル、51 文字のタイトル、存在しない ID、2回続けて完了。

**終わったと判断する目印:** 失敗のケースがすべて想定したステータスコードと JSON で返り、サーバーのログに例外のスタックトレースが出ない。

## 書き方の決まり

- `TaskService` と `ITaskRepository` には、HTTP に関わる型（`IResult`、`HttpContext`、ステータスコード）を出さない。
- `TaskService` の中で `new` してよいのはデータ（タスクや結果の型）だけ。依存する相手は DI から受け取る。
- `Program.cs` には「登録」と「エンドポイント」だけを書く。
- 例外を catch して何もせずに捨てない。
