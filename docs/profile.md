# 現在の業務領域と職種の整理

> 出典: 現在の業務領域と職種整理.pdf をもとに整理

## 1. 結論

現在の業務は、1つの職種では表せない。**複数のエンジニア職の領域を横断している。**

主軸となる職種:

- ソフトウェアエンジニア
- アプリケーションエンジニア（SE）／ プログラマー（PG）
- 社内SE ／ 業務改善SE
- AIアプリケーションエンジニア
- クラウド / インフラエンジニア
- ITアーキテクト的な業務の一部

### 業務比率（概ね）

| 領域 | 比率 |
|---|---|
| C++製品開発・改修 | 40% |
| 業務改善システムの要件定義・設計・開発 + 技術調査 / PoC | 20% |
| Dify・AI関連 + Azure / クラウド | 40% |

## 2. C++製品開発

### 担当範囲

- Windowsデスクトップアプリ、CAD・図形処理・GUI、業務アプリ
- 既存製品の機能追加・改修
- 既存製品から呼び出す新規ツール開発
- 一部の社内向けツール、顧客個別対応

設計は関数・クラス単位の実装設計から、画面・処理フロー・データ構造、
機能全体の構成・モジュール分割まで担当。
仕様が曖昧な状態から自分で詰めて実装することが多く、
案件によっては要求だけ渡されて設計から実装まで担当する。

### 実装内容

GUI以外に、業務ロジック・計算処理、ファイル入出力・設定ファイル処理、
CAD内部データ・幾何計算、帳票・印刷・出力処理、他モジュール・他アプリとの連携。

### 職種としての位置づけ

単なるPGではなく **アプリケーションSE + PG** に近い。
一般的な表現では **ソフトウェアエンジニア / アプリケーションエンジニア** が適する。

## 3. 業務改善・社内システム系

### 担当範囲（要望受領からの一気通貫）

```text
要望受領 → 必要機能の整理 → 要件定義 → 非機能要件整理
→ 技術調査 → 候補技術の比較 → PoC → 技術選定
→ アーキテクチャ設計 → 実装
```

技術選定では、候補の洗い出し、メリット/デメリット比較、
保守性・セキュリティ・コスト評価、PoCによる成立性確認、採用技術の提案、
最終決定への強い関与、アーキテクチャ全体の方式選定まで着手済み。
要件と技術方針の両方を自分が中心となってまとめている。

### 職種としての位置づけ

**社内SE / 業務改善SE** が主。技術選定・PoC・アーキテクチャ設計まで行うため
**ITアーキテクト的な業務も一部担当**。

ただし他エンジニアの設計統括や組織全体の技術標準策定までは行っていないため、
現時点では「アーキテクト職」そのものではなく
**アーキテクト領域まで担当するSE** という表現が適切。

## 4. AI・生成AI領域

### 担当範囲

- ChatGPT / Dify 等の業務利用
- Difyアプリ・Workflow構築、プロンプト設計、ナレッジ管理、RAG構成の調整
- モデル比較・選定
- OpenAI API を使ったシステム開発
- AIを組み込むべきか、どの方式にするかの検討
- AI精度評価・テスト方法の検討
- DB設計、外部API連携、バックグラウンド処理

### 職種としての位置づけ

最も近いのは **AIアプリケーションエンジニア** または **生成AI / LLMアプリケーションエンジニア**。
モデル学習・Fine-tuning・GPU基盤・MLOps を中心とするMLエンジニアとは異なる。

## 5. Azure / Dify運用・インフラ領域

### 現在の担当範囲

**Dify運用:**

- バージョンアップ判断、セキュリティ観点でのCVE確認、利用中ソフトへの影響調査
- 対応方針の検討、実際のアップデート
- 障害発生時の原因調査、復旧対応、ログ・DB・サーバー内部の確認、対応後の報告
- 運用方法の決定への強い関与
- 本番反映手順・切り戻し手順の検討、更新前の検証、性能・負荷・キャパシティ確認

**Azure:**

- 基本は既存環境の理解・操作が中心
- 最近は検証環境構成の検討、Azure CLIによるスナップショット作成、
  スナップショットからのVM作成、Blob共有構成の検討、スクリプト化による一部自動化にも着手

### 職種としての位置づけ

**インフラ / クラウド運用を担当するSE** が最も近い。
クラウド設計領域にも入り始めているため、今後はクラウドエンジニア寄りの比重が増える可能性がある。

## 6. SRE・セキュリティ領域

### SRE寄りの業務

担当している（SREと重なる）:

- 障害調査・復旧、ログ・メトリクス確認
- 停止時間を抑える方法の検討、更新前の検証環境確認
- ロールバック手順、性能・負荷確認

まだ担当していない:

- SLO / SLI の策定
- 本格的な監視設計
- CI/CD、大規模な運用自動化

→ SRE専任ではなく、**運用・信頼性確保の一部を担当している** という整理が適切。

### セキュリティ寄りの業務

CVE確認、影響調査、対応方針検討、アップデート・設定変更。
専任のセキュリティエンジニアではないが、運用・技術選定の中で
セキュリティ責任を一部担っている。

## 7. プロジェクト管理・チームリード

**通常のC++開発:**

- 自分に割り当てられた作業を担当
- 自分の工数・スケジュールを見積もる

**Dify・業務改善系:**

- 開発全体の作業項目・進め方の整理
- 他部署・上司との日程や優先順位調整
- リスク・課題の洗い出し、対応方針の検討

担当していない:

- 他メンバーへのタスク割り振り
- チーム全体の進捗管理、人員・コスト管理
- 他エンジニアの技術統括

→ 現時点では PM / PL が主職種ではない。

## 8. キャリアの捉え方

> C++アプリケーション開発を主軸としつつ、
> 社内業務改善・生成AI・クラウドまで担当する **フルサイクル寄りのソフトウェアエンジニア**

日本企業の職種名として簡潔に表すなら **SE（設計・開発） + 社内SE / 業務改善SE**。

最近は

```text
要件定義 → 技術選定 → PoC → アーキテクチャ設計 → 実装 → 運用
```

まで一人で担当する範囲が増えている。
従来の **SE + PG** から **フルサイクルエンジニア寄りの役割** へと
担当範囲が広がっていると整理できる。
