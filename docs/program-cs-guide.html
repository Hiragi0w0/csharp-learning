Program.cs は、サーバーの
「準備」と「受付」を書く場所

最初から各関数を暗記しなくていい。まず、コードがいつ実行されるかを2つに分けると読めるようになる。

このファイルの仕事は3つだけ。 機能を準備する → URLと処理を結ぶ → サーバーを起動して待つ。

最初に覚えるのは、2つの時間

同じ Program.cs に書いてあっても、全部が同じタイミングで動くわけではない。

アプリ起動時に1回 準備する時間

CreateBuilder、AddOpenApi、Build、Use...、Map... が、サーバーの構成を作る。

→
アクセスされるたびに何度でも 応答する時間

MapGet に渡したラムダが動き、天気データを作ってブラウザへ返す。

大事：MapGet(...) を書いた瞬間に天気データを作るわけではない。ここでは「このURLに来たら、この処理を呼ぶ」と登録している。

コードを4つの仕事に分ける

左を上から順に押して読む。最初は太字の一文だけで十分。

起動時に1回

サーバーを動かす準備

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}
app.UseHttpsRedirection();

必要な道具と、リクエストの通り道を準備している。

今していること

CreateBuilder が設定・ログ・サーバーの土台を用意し、AddOpenApi がOpenAPI機能を登録する。Build で設定を確定し、UseHttpsRedirection を通り道に追加する。

まだしていないこと

まだポートで待ち受けていない。天気データも作っていない。

ブラウザでURLを開いた後の流れ

ここからが「応答する時間」。1回アクセスされるたびに、この順で進む。

  1. 1受け取る
    Kestrel がHTTPリクエストを受け取る。

    例：GET /weatherforecast

  2. 2通り道を通る
    UseHttpsRedirection がHTTPならHTTPSへ案内する。

    HTTPSなら、そのまま次へ進む。

  3. 3行き先を探す
    登録済みの MapGet("/weatherforecast", ...) が見つかる。

    HTTPメソッドとパスの両方で照合する。

  4. 4処理を実行する
    ラムダが初めて動き、5件の WeatherForecast を作る。

    Select の処理は ToArray() で配列が必要になった時に実行される。

  5. 5返す
    配列をJSONへ変換して、ブラウザへ返す。

    配列を返したため、ASP.NET Core が application/json を選ぶ。

このページで必要な用語は5つだけ

Kestrel
ASP.NET Coreに組み込まれたHTTPサーバー。外から来たリクエストを最初に受け取る。
DIコンテナ
必要な部品を登録し、必要になった場所へ渡す仕組み。今は「部品置き場」くらいでいい。
ミドルウェア
リクエストがエンドポイントへ届く前後に通る共通処理。HTTPSへの転送など。
エンドポイント
「HTTPメソッド + URL」と、実行する処理を結びつけた受付口。
JSON
データを文字として送る形式。C#の配列やオブジェクトから自動変換される。

理解を確認する3つの実験

読むより、1か所変えて結果を見るほうが早い。変更前にコミットする必要はまだない。

app.Run() を一時的にコメントアウト

実行すると、待ち受ける処理がないためアプリがすぐ終了する。

分かること：Run がサーバーを起動し、終了まで待っている。

MapGet の戻り値を文字列にする

新しいURLで () => "hello" を返す。ブラウザではJSONではなく文字列になる。

分かること：戻り値の型を見て、ASP.NET Core がレスポンス形式を選んでいる。

同じURLへ2回アクセス

天気の数値やSummaryが変わるか見る。

分かること：ラムダは起動時ではなく、リクエストのたびに実行されている。
