Program.cs を読む

「何をしてるか」を 3つのフェーズ と 1リクエストの旅 で見る。各行の細かい中身は開いて読む。

1全体は3フェーズ

① 登録〜 Build()

サービスをカタログに並べる

→
② 組み立てBuild() 〜 Run()

リクエストの通り道を組む

→
③ 実行Run() 〜

ポートを開いて待つ

①②は起動した瞬間に終わる。リクエストを処理するのは ③だけ。「登録した時点では実行されていない」がここ。

21リクエストの旅

  1. 外ブラウザが接続してくる
  2. サーバーKestrel が受け取る
  3. 準備HttpContext を作る（メソッド・パス・ヘッダ・ボディ）
  4. 関所UseHttpsRedirection → httpなら 307 を返してここで終わり
  5. 振り分けルーティング → URLに合うハンドラを探す
  6. 実行ラムダが走る（天気データを作ってるのはここ）
  7. 整形戻り値の型を見て JSON に変換、Content-Type を付ける
  8. 外レスポンスを書き込んでブラウザへ

3各行がしていること

1var builder = WebApplication.CreateBuilder(args);

アプリの土台を作る。1行に見えて6つくらいやってる。

中で起きていること
  • args（コマンドライン引数）を設定として載せる
  • 設定を読む（優先順位: 環境変数 > appsettings.json）
  • ログの仕組みを組み立てる
  • DIコンテナを新しく作る（まだ空っぽの対応表）
  • Kestrel（HTTPサーバー本体）の設定を用意する
  • まだポートは開かない

返ってくるのは「設定を溜めておく箱」。

5builder.Services.AddOpenApi(); Add

対応表に1行足すだけ。まだ何も作ってない。

中で起きていること
  • builder.Services の中身は「型 → 実装」の対応表（辞書）
  • そこに「OpenAPIを作る係はこれを使う」と1行登録する
  • インスタンスは作らない。誰かに要求されたときに初めて作る（遅延生成）

これが DI の正体。自分で new する代わりに「要るなら作って」と予約しておく。

7var app = builder.Build();

表を確定させて、実際に組み立てる。ここが一番大きい。

中で起きていること
  • 登録された対応表から ServiceProvider ができる
  • ミドルウェアを積むための器ができる
  • Kestrel が構成される（まだ起動しない）
  • ここで対応表は書き換えられなくなる

だから Add は Build より前、Use / Map は Build より後。順番が決まってるのはこれが理由。

10if (app.Environment.IsDevelopment())

環境名を比べて bool を返すだけ。魔法は無い。

中で起きていること
  • 環境名は ASPNETCORE_ENVIRONMENT 環境変数から来る
  • dotnet run のときは Properties/launchSettings.json が設定している
  • だから「開発中だけ実行される分岐」になる。11〜13行目を消しても本番には影響しない
12app.MapOpenApi(); Map

自分のAPIの説明書を返すエンドポイントを1本足す。

中で起きていること
  • 既定のURLは /openapi/v1.json
  • リクエストが来たら、登録済みのエンドポイントを走査してパス・メソッド・返り値の型を集める
  • 情報源は MapGet で登録した内容

実行時にルーティング表を読むので、書く順番は関係ない。

15app.UseHttpsRedirection(); Use

通り道に関所を1枚挿す。httpなら https へ飛ばす。

やっていることは地味 
httpか?
 ├─ Yes → Location を付けて 307 を返す（次の関所へは行かない）
 └─ No  → 何もせず次へ通す

体感できる。http://localhost:5xxx を開くと勝手に https://localhost:7xxx に飛ぶ。あれがこの行。

22app.MapGet("/weatherforecast", () => { … }) Map

URLと処理を結ぶ。登録するだけで、まだ実行しない。

中で起きていること
  • ルーティング表に「GET + /weatherforecast → このラムダ」を1行登録
  • ラムダはリクエストが来たときだけ走る
  • 24行目の LINQ はその場で走らない。.ToArray() の瞬間に走る（遅延評価）
  • つまり1リクエストごとに作り直している
34.WithName("GetWeatherForecast")

エンドポイントに名前を付けるだけ。

名前は何に使う?
  • ① 別の場所から URLを逆引きするため
  • ② OpenAPI の operationId になる（説明書に載る）
36app.Run();

ここで初めてポートを開いて待ち受ける。

中で起きていること
  • ホストを開始して、停止シグナルを待つ状態でブロックする
  • Ctrl + C で止まるのは、ここでシグナルを拾って終了処理をしているから
  • Ctrl + C しないとプロセスが残る → さっきの MSB3026
38record WeatherForecast(DateOnly Date, int TemperatureC, string? Summary)

データの型を定義している。変換はしていない。

中で起きていること
  • コンパイラが裏で作る: コンストラクタ / 読み取り専用プロパティ / Equals / GetHashCode / ToString / Deconstruct
  • string? の ? はnull許容参照型。実行時ではなくコンパイル時に警告を出す仕組み

38行目 = 型の定義、40行目 = その型の計算プロパティ。ここがノートで混ざっていたところ。

40public int TemperatureF => 32 + (int)(TemperatureC / 0.5556);

摂氏→華氏の変換はここ。式形式プロパティ。

中で起きていること
  • => は「get だけのプロパティ」。値を保持せず呼ばれるたびに毎回計算する
  • get があるので JSONにも出力される（返ってきたJSONに temperatureF があるか見てみる）

4おせっかいの正体（戻り値の扱い）

ラムダが何を返すかで、フレームワークの扱いが変わる。

返した型フレームワークがすること
stringそのまま text/plain
オブジェクト / 配列JSONに変換、application/json ← forecast はこれ
IResult（Results.Ok() など）自分で制御。ステータスコードも指定できる

5Add / Use / Map の3種類

「Add というメソッド」があるわけじゃない。接頭辞のグループ。

グループ何をしてるかこのファイルでは
Addサービス登録（DIコンテナに登録）AddOpenApi() 5行目
Use通り道に挟む（全部のリクエストが通る）UseHttpsRedirection() 15行目
Mapエンドポイント（URLと処理を結ぶ）MapOpenApi() / MapGet()

2つしかないのは、このテンプレートが最小構成だから。コントローラー方式なら AddControllers() が並び、認証を足すと AddAuthentication() / UseAuthentication() / UseAuthorization() が増える。Add/Use は後から増えていくもの。

Add は builder.Services に生えている = 触ってるのは DIコンテナ
Use / Map は app に生えている = 触ってるのは通り道

6「具体的」は5分で確かめられる

  1. http://localhost:5xxx/weatherforecast を開く → httpsに飛ぶ = 15行目
  2. /openapi/v1.json を開く → 説明書が出る = 12行目
  3. F12 → Network で 307 と Content-Type: application/json を見る
  4. 返ってきたJSONに temperatureF があるか確認 → 40行目
  5. 36行目の app.Run(); をコメントアウトして実行 → 一瞬で終わる

5番が一番効く。動かない状態を作ると、その行が何をしていたか分かる。
