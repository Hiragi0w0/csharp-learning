# 学習プラン

`docs/job-map.md` の「伸ばす余地がある領域」から、実際に手を動かすテーマを選ぶ。
方針は **1テーマ=小さく1つ作り切る**。読むだけの学習は最小限にする。
学び方は、**文法とネットワークを分けず、1つの動く題材の中で一緒に**進める。
最終的に学ぶ対象は **言語そのものではなく、ネットワークと設計**で、C# は題材（手段）として使う。

テーマを選ぶ基準は **業務で使うかどうかではなく、キャリアに効くかどうか**。
具体的には「転用が効くか」「職種名として市場で通るか」「今の強みと掛け算できるか」。

## 進め方（AIと一緒にやる前提）

1. テーマを1つ選ぶ（下の候補から、または自分で追加）。
2. 「なぜこれを学ぶのか」を1行で書く。**キャリアのどの場面で効くか**の形で書く。
3. 到達点（Done when）を先に決める。**動くもので判定できる形**にする。
4. 環境を用意する → 最小構成で1つ動かす → 崩して理解する。
5. 詰まったらAIに聞く。聞き方は `AGENTS.md` の Goal / Context / Constraints / Done when。
6. 学んだことを `notes/` に残す。

AIへの指示は「実装して」ではなく、

- 「この設計で良いか review して」
- 「このエラーはどこを疑うべきか、確認手順を出して」
- 「このコードの責務分離は妥当か、理由つきで指摘して」

のように、判断を求める形にする。

## テーマ候補

### A. C# バックエンド（ASP.NET Core）— 進行中

- **決定（2026-09-24）: C# は WPF ではなくバックエンドから入る。WPF は保留。**
  （社内ツールのGUIを実際に作る予定が出たら、その時に着手する）
- なぜ（キャリア視点）:
  - 転用が効く。Webの基礎（HTTP・認証・DB・デプロイ）はどの現場でも使う。
  - 職種名として市場で通る。「バックエンドエンジニア / サーバーサイド」は求人・書類で通用する棚。
    WPF は今の C++ と同じ「Windowsアプリ」の棚で、市場も狭い。
  - 掛け算ができる。C#バックエンド × 生成AI × Azure × 業務知識は今の強い組み合わせ。
- 学び方（**今ここ**）: **文法とネットワークを分けず、1つの動く題材の中で一緒に**進める。
  題材は最小Web API（`dotnet new webapi`）。文法が目的を持つと定着する。
  到達点: APIが1本動き、コードを「C++との違い」と「HTTPとして何が起きているか」の両方で説明できる。
- 次の段階: 外を叩く側を書く（`HttpClient`、タイムアウト、リトライ、失敗する前提の設計）。
- その次の段階: **設計**。DI、責務分離、依存の向き、エラーの設計、トレードオフの言語化。
- この先（今週はやらない）: DB（EF Core / SQLite）、認証、Azureへのデプロイ、CI/CD。

### B. Azure の設計と自動化

- なぜ: 今は既存環境の操作が中心。設計側に比重を移せる。クラウドは職種として独立して強い。
- 到達点の例: Azure CLI で検証環境（VM + ストレージ）を作るスクリプトを書き、作り直せる。
- 触れる要素: Azure CLI、リソースグループ、ネットワーク、スナップショット、コスト感覚、IaC（Bicep/Terraform）。
- つながり: A の後に来る。C#バックエンドが書けると、デプロイ先としてAzureが自然につながる。

### C. SRE の入口

- なぜ: 障害対応は担当しているが、SLO/SLI と監視が薄い。運用を語れる人は少ない。
- 到達点の例: 対象を1つ決め、SLI を定義して簡単な監視・アラートを置く。
- 触れる要素: SLI/SLO/エラーバジェット、ログ設計、メトリクス、アラート疲れ、ランブック。

### D. CI/CD と自動化

- なぜ: 未着手で、どの現場でも前提になっている。できないと評価が上がらない。
- 到達点の例: 自分の練習用リポジトリで build → test → 成果物 まで自動で回す。
- 触れる要素: GitHub Actions、キャッシュ、シークレット管理、バージョニング。

### E. AIアプリ（RAG）の評価

- なぜ: 構築は担当しているが、評価を数値で語る部分が弱い。
  ここを語れると「AIを使える人」から「AIを評価できる人」に上がる。
- 到達点の例: 小さなRAGに対して評価用データセットを作り、指標で改善前後を比較する。
- 触れる要素: 検索精度、回答の根拠提示、プロンプト設計、テスト設計。

### F. 設計力（アーキテクチャ）

- なぜ: 方式設計まで担当しているが、判断基準を言語化できていない。
  ※ これは実務の延長なので、働きながら常時取り組む枠にする。
- 到達点の例: 過去案件を1つ選び「なぜこの方式にしたか」を他者に説明できる形で書き出す。
- 触れる要素: 責務分離、依存の方向、トレードオフの書き方、ADR（意思決定の記録）。
